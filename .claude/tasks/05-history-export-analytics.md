# ТЗ-05: История сессий, экспорт и аналитика использования

**Размер:** L (3-4 недели)
**Приоритет:** 🟠 Phase 3 — нужно для retention и для самообслуживания пользователя

---

## 1. Контекст и зачем

Сейчас в «Параграфе» сессии чата хранятся (opencode использует SQLite локально),
и в сайдбаре есть список «История». Но нет:
- **Полноценного управления историей**: поиск, фильтры, переименование, удаление,
  группировка по дате/сценарию/вертикали
- **Экспорта сессии** целиком (вся переписка → DOCX/PDF/Markdown) — юристу нужно
  приложить «как ИИ анализировал договор» к делу
- **Аналитики использования**: сколько кредитов потрачено на что, по каким моделям,
  по каким сценариям — для самоконтроля расходов

Это закрывает две потребности: **retention** (юзер возвращается к прошлым работам)
и **прозрачность расходов** (видит куда уходят кредиты, доверяет биллингу).

## 2. Объём

**В скоупе:**
- **История сессий**: список с поиском по содержимому, фильтры (дата, вертикаль,
  сценарий, модель), сортировка, переименование, удаление, закрепление (pin)
- **Полнотекстовый поиск** по сообщениям всех сессий
- **Экспорт сессии**: вся переписка → DOCX / Markdown / PDF (через существующий
  doc-export пайплайн)
- **Группировка**: «Сегодня / Вчера / На этой неделе / Раньше», и по сценарию
- **Дашборд аналитики**: график расхода кредитов по дням, разбивка по моделям,
  топ сценариев, средняя стоимость задачи
- **Экспорт аналитики** в CSV (для бухгалтерии фирмы)

**Не в скоупе:**
- Облачная синхронизация истории между устройствами — Phase 4
- Командный доступ к чужим сессиям — Phase 4
- AI-поиск (семантический) — на MVP полнотекстовый

## 3. Источники данных

### 3.1 Сессии и сообщения
opencode хранит сессии локально (SQLite через core). Нужно понять текущую схему:
- Найти где opencode хранит сессии/сообщения (`packages/core` или `packages/opencode`
  — искать `session`, `message` таблицы, sync-слой `useSync`/`sync.data`)
- Переиспользовать существующий доступ (`sync.data.session`, `sync.data.message`,
  `sync.data.part`), НЕ дублировать хранилище

### 3.2 Аналитика расходов
billing уже пишет `usage_events` (model, input_tokens, output_tokens, credits_charged,
scenario_id, created_at — см. `billing/src/db/schema.ts`). Нужен новый endpoint:

```
GET /usage/summary?from=2026-05-01&to=2026-05-31
→ {
    totalCredits: 1234,
    byDay: [{ date, credits }, ...],
    byModel: [{ model, credits, requests }, ...],
    byScenario: [{ scenarioId, title, credits, requests }, ...],
    avgCreditsPerRequest: 12.3
  }

GET /usage/events?from=...&to=...&limit=...&offset=...
→ { items: [{ model, credits, scenarioId, createdAt }], total }
```

## 5. UI — Экспорт сессии

Кнопка «Экспорт» в карточке сессии и в открытой сессии (⋯ меню):
- Модалка выбора формата: DOCX / Markdown / PDF
- Опции: «включить системные сообщения», «включить метаданные (модель, дата, кредиты)»
- Сборка: вся переписка → структурированный документ:
  ```
  # Сессия: {title}
  Дата: {date} · Модель: {model} · Потрачено: {credits} кредитов

  ## Вопрос (Вы)
  {user message}

  ## Ответ (Параграф)
  {assistant message}
  ...
  ```
- DOCX — через существующий `doc-export.ts` (markdownToDocxBlocks)
- PDF — новый рендерер (можно через тот же docx → конвертация, или jsPDF/pdf-lib)
- Markdown — простая конкатенация

Реюз `desktop/packages/app/src/ourapp/doc-export.ts`.

## 10. Подводные камни

- **Не дублировать хранилище сессий.** opencode уже хранит сессии. Изучить
  `sync.data.session/message/part` и строить поверх, иначе будет рассинхрон.
- **Полнотекстовый поиск по большой истории** — если сессий сотни, наивный перебор
  всех сообщений тормозит. Для MVP — приемлемо (юзеров с 1000+ сессий нет), но
  заложить дебаунс и лимит. SQLite FTS5 — если доступен в opencode-слое.
- **PDF-генерация** — нет нативного рендерера. Варианты: (а) docx → не даёт PDF
  напрямую; (б) pdf-lib/jsPDF — кириллица требует встроенного шрифта (подключить
  тот же IBM Plex/Onest как base64); (в) печать через Electron `webContents.printToPDF`
  — самый надёжный для кириллицы. Рекомендую (в) для desktop.
- **usage_events наполнение.** Критично проверить что billing реально пишет расход
  на каждый запрос. Если Gateway (LiteLLM) не шлёт расход в billing — аналитика
  будет пустой. Это может быть отдельная подзадача (ETL из LiteLLM spend → usage_events;
  есть `billing/src/worker/etl.ts` — проверить работает ли).
- **Часовые пояса.** «Сегодня/Вчера» считать в локальной TZ пользователя, не UTC.
- **Экспорт больших сессий.** Сессия на 100+ сообщений → большой DOCX. Не блокировать
  UI — генерить асинхронно с прогрессом.
- **Приватность экспорта.** Если включено маскирование ПДн (ТЗ-04) — экспортировать
  РЕАЛЬНЫЕ данные (они локальные), не маскированные. Согласовать с ТЗ-04.
