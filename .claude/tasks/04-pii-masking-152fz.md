# ТЗ-04: Маскирование персональных данных (152-ФЗ)

**Размер:** L (3-4 недели)
**Приоритет:** 🔴 Юридически обязательно для РФ-рынка — без этого нельзя продавать легально

---

## 1. Контекст и зачем

«Параграф» отправляет документы пользователей (договоры, требования ФНС, первичка)
в облачные LLM (Claude/GPT — хостинг США/ЕС). Эти документы содержат **персональные
данные** (ПДн): ФИО, паспорта, ИНН, СНИЛС, адреса, телефоны, реквизиты карт.

По **152-ФЗ «О персональных данных»** трансграничная передача ПДн в недружественные
юрисдикции без согласия и без мер защиты — **нарушение** с оборотными штрафами
(до 18 млн ₽ за повторное нарушение с 2025). Это **главный юридический риск** проекта
(см. план §9.3).

Решение — **локальное маскирование ПДн перед отправкой**: на машине пользователя
(в renderer/desktop), ДО того как текст уходит в Gateway, чувствительные данные
заменяются на плейсхолдеры (`[ФИО-1]`, `[ПАСПОРТ-1]`). Модель работает с
обезличенным текстом. При получении ответа — **обратная подстановка** (демаскирование),
чтобы пользователь видел реальные данные.

**Ключевой принцип:** реальные ПДн **никогда не покидают машину пользователя**.
Маппинг плейсхолдер→значение хранится только локально в памяти сессии.

## 2. Объём

**В скоупе:**
- Детекторы ПДн для РФ: ФИО, паспорт (серия+номер), ИНН (физ/юр), СНИЛС, адрес,
  телефон, email, номер карты, ОГРН/ОГРНИП, расчётный счёт, дата рождения
- Маскирование текста перед отправкой + демаскирование ответа
- Консистентность: одно и то же значение → один плейсхолдер в рамках сессии
  (чтобы модель понимала что «Иванов» в начале и в конце — один человек)
- UI-переключатель «Защита ПДн» (вкл/выкл) в настройках + индикатор в composer
- Превью «что будет замаскировано» перед отправкой (опционально, по флагу)
- Режимы: строгий (маскируем всё) / мягкий (только паспорт/карта/СНИЛС — самое чувствительное)
- Whitelist: не маскировать названия гос. органов, статьи законов, публичные реквизиты
- Тесты на реальных образцах документов

**Не в скоупе:**
- ML-based NER (named entity recognition) — на MVP только regex + словари. ML позже.
- Маскирование внутри изображений/сканов (OCR-маскинг) — Phase 3
- Серверное маскирование — принципиально только клиентское (ПДн не должны доходить до Gateway)

## 3. Архитектура

```
Пользователь вводит текст / прикрепляет документ
            │
            ▼
   ┌─────────────────────┐
   │  PII Detector        │  regex + словари (ФИО), РФ-специфика
   │  → список Match[]    │  (тип, позиция, значение)
   └─────────┬───────────┘
             ▼
   ┌─────────────────────┐
   │  Masker              │  значение → плейсхолдер, строит Vault
   │  → maskedText        │  (консистентный маппинг в рамках сессии)
   │  → Vault(map)        │
   └─────────┬───────────┘
             ▼
     maskedText уходит в Gateway → LLM
             │
             ▼ ответ модели (с плейсхолдерами)
   ┌─────────────────────┐
   │  Unmasker            │  плейсхолдер → реальное значение из Vault
   │  → реальный ответ    │
   └─────────────────────┘
             ▼
     Пользователь видит ответ с реальными ПДн
```

**Vault** — in-memory `Map<placeholder, realValue>`, живёт в рамках сессии чата.
Не сохраняется на диск, не уходит в сеть, очищается при закрытии сессии.

## 4. Детекторы ПДн (РФ-специфика)

Файл `desktop/packages/app/src/ourapp/pii/detectors.ts`. Каждый детектор — функция
`(text: string) => PiiMatch[]`.

```ts
export interface PiiMatch {
  type: PiiType
  start: number      // позиция в тексте
  end: number
  value: string      // оригинальное значение
  confidence: number // 0..1 — для приоритезации при пересечениях
}

export type PiiType =
  | "fio"            // ФИО
  | "passport"       // паспорт РФ (серия 4 цифры + номер 6 цифр)
  | "inn_person"     // ИНН физлица (12 цифр)
  | "inn_org"        // ИНН юрлица (10 цифр)
  | "snils"          // СНИЛС (XXX-XXX-XXX YY)
  | "ogrn"           // ОГРН (13) / ОГРНИП (15)
  | "bank_account"   // расчётный счёт (20 цифр)
  | "card"           // номер карты (16 цифр, Luhn-проверка)
  | "phone"          // телефон РФ (+7/8...)
  | "email"
  | "address"        // адрес (улица, дом, кв)
  | "birthdate"      // дата рождения
```

### Конкретные правила (важно — точность критична):

- **Паспорт:** `\b(\d{2}\s?\d{2})\s+(\d{6})\b` — но не путать с другими 10-значными.
  Контекст-маркеры рядом: «паспорт», «серия», «выдан».
- **ИНН:** 10 или 12 цифр + **контрольная сумма** (алгоритм ФНС). Без контрольной
  суммы — высокий false-positive. Реализовать валидатор ИНН.
- **СНИЛС:** `\d{3}-\d{3}-\d{3}\s\d{2}` + контрольная сумма.
- **Карта:** 16 цифр + **алгоритм Луна** (Luhn). Без Luhn — ловит любые 16-значные.
- **ОГРН:** 13/15 цифр + контрольная сумма.
- **Расчётный счёт:** 20 цифр, обычно с маркером «р/с», «счёт».
- **Телефон:** `(\+7|8)[\s\-(]?\d{3}[\s\-)]?\d{3}[\s\-]?\d{2}[\s\-]?\d{2}`.
- **ФИО:** самое сложное. Словарь частых русских фамилий/имён/отчеств +
  паттерн «Фамилия И.О.» / «Фамилия Имя Отчество» с заглавных. Отчества на
  `-вич/-вна/-ьич` — сильный маркер. Использовать **словарь отчеств-окончаний**.
- **Адрес:** маркеры «г.», «ул.», «д.», «кв.», «обл.», индекс (6 цифр).
- **Дата рождения:** `\d{2}\.\d{2}\.\d{4}` рядом с «р.», «род.», «дата рождения».

### Whitelist (НЕ маскировать):
- Названия гос. органов: «ФНС», «Роскомнадзор», «ИФНС №...», «МВД» и т.д.
- Ссылки на статьи: «ст. 614 ГК РФ», «п. 1 ст. 23 НК РФ»
- Реквизиты самих гос. органов (публичные ИНН ведомств — словарь)
- Юридические термины

Файл `desktop/packages/app/src/ourapp/pii/whitelist.ts`.

## 5. Маскер / Демаскер

Файл `desktop/packages/app/src/ourapp/pii/masker.ts`:

```ts
export interface MaskResult {
  maskedText: string
  vault: PiiVault   // плейсхолдер → реальное значение
  stats: Record<PiiType, number>  // сколько чего замаскировано
}

export class PiiVault {
  private map = new Map<string, string>()        // placeholder → value
  private reverse = new Map<string, string>()    // value → placeholder (консистентность)
  private counters = new Map<PiiType, number>()

  /** Получить/создать плейсхолдер для значения (консистентно в рамках vault). */
  placeholderFor(type: PiiType, value: string): string {
    const norm = normalizeValue(type, value)   // нормализация (убрать пробелы в паспорте и т.п.)
    const existing = this.reverse.get(norm)
    if (existing) return existing
    const n = (this.counters.get(type) ?? 0) + 1
    this.counters.set(type, n)
    const ph = `[${LABEL[type]}-${n}]`          // [ФИО-1], [ПАСПОРТ-2]
    this.map.set(ph, value)
    this.reverse.set(norm, ph)
    return ph
  }

  /** Демаскировать: заменить плейсхолдеры обратно на реальные значения. */
  unmask(text: string): string {
    let out = text
    for (const [ph, value] of this.map) {
      out = out.replaceAll(ph, value)
    }
    return out
  }
}

export function maskText(text: string, options: MaskOptions): MaskResult { ... }
```

**Пересечения матчей:** если два детектора захватили пересекающиеся диапазоны —
выбираем по `confidence`, затем по длине. Сортировать matches по start, разрешать
конфликты, применять справа налево (чтобы не сбить позиции).

## 6. Интеграция в pipeline отправки

Точка вставки — там же, где формируется текст запроса (`submit.ts → draftText()`
или `build-request-parts.ts`). Логика:

```ts
// ПЕРЕД отправкой
if (piiProtectionEnabled()) {
  const { maskedText, vault } = maskText(fullPrompt, { mode: piiMode() })
  sessionVaults.set(sessionID, vault)   // сохраняем vault для демаскирования ответа
  return maskedText  // в Gateway уходит обезличенный текст
}

// ПОСЛЕ получения ответа (в рендере сообщения ассистента)
const vault = sessionVaults.get(sessionID)
const displayText = vault ? vault.unmask(rawAssistantText) : rawAssistantText
```

**Важно:** демаскирование происходит **только при отображении** (в renderer),
не сохраняется обратно в историю замаскированным. Решить: хранить ли в локальной
истории сессий маскированную или реальную версию (рекомендую — реальную локально,
раз ПДн и так на машине юзера; маскирование только для исходящего трафика).

## 7. UI

### 7.1 Переключатель в Settings
Новая секция «Защита персональных данных»:
- Тумблер «Маскировать ПДн перед отправкой в облачные модели» (по умолчанию ВКЛ)
- Радио режима: «Строгий» (всё) / «Мягкий» (паспорт/карта/СНИЛС)
- Пояснение: «Включено: паспорта, ИНН, ФИО и др. заменяются на метки перед
  отправкой. Российские модели (GigaChat) — данные остаются в РФ, маскирование не нужно.»
- Чекбокс «Показывать что замаскировано перед отправкой» (превью)

Хранение — localStorage + (опц.) синк в billing-профиль.

### 7.2 Индикатор в composer
Маленький бейдж рядом с кнопкой отправки: 🛡 «Защита ПДн» (если включено).
При клике — поповер с кратким объяснением + ссылка в Settings.

### 7.3 Превью маскирования (опционально)
Если включён чекбокс «показывать» — перед отправкой модалка:
«Будет замаскировано: 3 ФИО, 1 паспорт, 2 ИНН. [Отправить] [Отмена]».
С подсветкой замаскированных фрагментов в тексте.

### 7.4 Автоотключение для РФ-моделей
Если выбрана GigaChat/YandexGPT (хостинг РФ) — маскирование не нужно (данные не
покидают РФ). Показывать: «Выбрана российская модель — маскирование не требуется».

## 9. Тесты (критично — точность важнее всего)

`pii.test.ts` должен покрывать:
- [ ] Каждый детектор на позитивных примерах (реальный паспорт/ИНН/СНИЛС/карта)
- [ ] **Контрольные суммы:** валидный ИНН проходит, ИНН с битой контрольной — НЕ ловится
- [ ] Luhn: валидная карта ловится, случайные 16 цифр — нет
- [ ] Whitelist: «ст. 614 ГК РФ» НЕ маскируется, «ИНН ФНС» — нет
- [ ] Консистентность: «Иванов» в двух местах → один плейсхолдер `[ФИО-1]`
- [ ] Round-trip: maskText → unmask возвращает исходный текст
- [ ] Пересечения: паспорт внутри которого цифры похожи на ИНН — выбирается правильный
- [ ] Режимы: мягкий маскирует только паспорт/карту/СНИЛС, строгий — всё
- [ ] Реальный договор-образец: проверить что ФИО сторон, паспорта, реквизиты замаскированы, а статьи ГК и названия — нет

## 10. Подводные камни

- **False positives дороже false negatives** для UX, но **false negatives дороже
  для закона**. Баланс: контрольные суммы (ИНН/СНИЛС/карта/ОГРН) резко снижают FP.
  ФИО — самый шумный детектор, словарь + паттерн отчества обязательны.
- **Позиции при замене.** Применять замены справа налево (от конца текста), иначе
  сдвигаются позиции последующих матчей.
- **Нормализация значений** для консистентности: «77 12 345678» и «7712 345678» —
  один паспорт. Нормализовать перед сравнением в Vault.
- **Демаскирование частичных совпадений.** Если модель в ответе разбила плейсхолдер
  (`[ФИО -1]` с пробелом) — unmask не сработает. Использовать плейсхолдеры устойчивые
  к токенизации (без пробелов, например `«ФИО_1»` или `__PII_FIO_1__`). Тестировать
  на реальных ответах Claude/GPT — они иногда «чинят» форматирование.
- **Streaming.** Ответ приходит по токенам. Демаскировать на лету сложно (плейсхолдер
  может прийти разорванным между чанками). Решение: демаскировать только финальный
  полный текст, либо буферизовать. Streaming-демаскинг — известная сложность, заложить время.
- **ФИО иностранцев / редкие фамилии** — словарь не покроет. Паттерн «Слово Слово
  Слово-вич/вна» поможет, но не идеально. Документировать ограничение.
- **GigaChat-исключение.** Для РФ-моделей маскирование вредит (модель хуже понимает
  обезличенный текст, а данные и так в РФ). Обязательно автоотключение по провайдеру.
- **Юридическая формулировка.** Точные тексты согласия на обработку ПДн и описание
  мер — согласовать с юристом. В коде — заглушки-тексты, помеченные `// LEGAL: review`.
